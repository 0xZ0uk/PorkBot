# v1.0 acceptance run

This is the turnkey script for issue #105: the human run that walks the PRD
stories 1–48 and every ratified parity-ledger row on a real deployment and
records the evidence. It closes v1.0 or it names what blocks it.

Nothing here replaces the PRD ([issue #1](https://github.com/0xZ0uk/PorkBot/issues/1));
the stories are quoted by number, the verdicts come from the ratified ledger
([issue #14](https://github.com/0xZ0uk/PorkBot/issues/14)), and the deferred
rows point at the v1.1 backlog issues (`#169`–`#188`).

## How to run it

1. Record the run header in a comment on #105: candidate commit, host
   specification, date, operator.
2. Provision one host to the documented floor (4 vCPU and 8 GB RAM, plus each
   concurrently active bot's memory share and every configured bot's disk).
   Disk is the measured image and home terms plus the write-layer budget
   `PORKBOT_COMPUTER_DISK_MB`, enforced only where the daemon's storage driver
   answers it; leave room for the images and the bounded snapshot store. A
   clean host is also the rehearsal for the
   [clean-host install](https://github.com/0xZ0uk/PorkBot/issues/106).
3. Install Docker Engine + Compose, Node 24 and pnpm 10, clone the candidate
   commit, then `pnpm install`.
4. `pnpm deploy:setup --origin https://<host>` and `pnpm deploy:up`. The
   [self-host guide](self-host.md) is the runbook. Keep `deploy/.env` out of
   the evidence: it holds every generated secret.
5. Open the first sign-in (story 3), create one model connection (story 12), one
   bot (story 16) and its computer (story 27). Later stories need that baseline.
6. Walk each item below, attach its evidence to #105, and tick the box.
7. Scrub before posting: no hostnames, addresses, personal emails, account ids
   or key ids in the evidence. This repository is public and the issue is too.
   Describe results in words; never paste raw tool output.

Evidence is one of: screenshot, log excerpt, run id, or CI job link. Each story
names the test that proves it in CI as well; when the deployment walk and the
suite disagree, the deployment is right and the suite has a bug.

## 1. Stories 1–48

### Operations

**1 — Run the whole product on one VPS with Docker Compose.**
Walk: `pnpm deploy:up` on the clean host; wait for every healthcheck.
Expect: the message naming the stack healthy, then `pnpm deploy:status` with
postgres, migrate (exited 0), backup (exited 0), api, worker, web, supervisor and proxy

Evidence: deploy log excerpt, status output, host spec.

pnpm deploy:upgrade --tag <sha>             # pull, preflight, migrate, switch
pnpm deploy:rollback                        # redeploy the recorded prior tag
pnpm stack:up / pnpm stack:down             # local stack, same topology
pnpm test / pnpm test:integration / pnpm test:e2e
pnpm lint / pnpm typecheck / pnpm build / pnpm test:coverage
pnpm docs:check / pnpm quarantine:check / pnpm dependencies:check / pnpm env:check
pnpm desktop:package / pnpm desktop:smoke
pnpm release:notes
